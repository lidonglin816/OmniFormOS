1. 项目概述与产品定位

OmniFormOS 把"一句话描述业务问题"到"可运行的业务应用"之间的链路拆成八个专业引擎，每个引擎负责一类业务对象的完整生命周期：建模、编辑、运行、统计。桌面版将该能力封装为离线可用的 Windows 应用，数据以本地 SQLite 工作区保存。

1.1 产品定位

  • 目标用户：高校院系与社团、中小企业业务管理岗、需要快速验证管理流程的个人开发者。
  • 核心价值：把表单/流程/题库/数据集这类"重复造轮子"的业务系统，压缩为一次意图描述 + 少量明确指令的迭代。
  • 交付形态：桌面安装包（内置运行环境，双击即用）+ 同构网页工作区（便于评审快速访问）。

2. 意图控制策略

低代码平台的核心难题不是"能不能生成"，而是"生成结果是否可控、可回退、可解释"。本项目采用四层递进策略：收敛输入空间 → 约束输出结构 → 明确降级边界 → 全程可观测。

2.1 第一层：输入空间收敛

自然语言的自由度必须被收窄到模型或规则引擎可以稳定处理的范围内，否则同一句话会产出结构差异巨大的结果，用户无法预期。

  • 场景模板入口：主页提供客户、报销、库存、项目等预设芯片，点击即填入结构化示例需求，把"开放式描述"转化为"模板 + 差异描述"。
  • 指令式迭代语法：定义明确可解析的增量指令族，例如"添加字段：预算，类型：数字，必填""新增实体：合同""新增角色：经理""应用名称改为我的系统"。这类指令走确定性解析路径，不依赖模型，结果可预测。
  • 结构化需求表达：对复杂配置（如设置界面九大栏目），实际开发中采用表格化需求输入（见第 7 章），把模糊的"做得好一点"替换为可验收的字段清单。

2.2 第二层：输出结构约束

所有 AI 产出一律先转成结构化中间态，再进入渲染与持久化，禁止模型输出直接注入界面。

环节中间态校验内容
AI 出题题目数组 JSON题型枚举、题干非空、选项数量、答案存在性、分值区间；不合格条目退回，不进入题库
应用生成应用蓝图 Schema实体唯一性、字段类型合法性、关联目标存在性；校验通过才允许预览
流程生成节点/边图结构必须存在唯一开始节点与终止节点、无孤立节点、审批人非空；图校验失败禁止发布
文档解析字段定义列表类型推断、必填推断、取值范围；全部标注来源页与坐标，供人工复核

校验失败时界面给出具体原因（哪一项、哪个字段），而不是笼统的"生成失败"，使用户能给出更精确的修正指令，形成闭环。

2.3 第三层：能力边界与降级

平台明确区分"确定性能力"与"模型能力"，并在模型不可用时给出可见降级，不伪装成功。

  • 确定性能力：表单校验、流程流转、评分计算、聚合统计、数据库增删改查——不依赖大模型，离线可用。
  • 模型能力：需求理解生成、AI 出题、文本抽取增强——依赖 OpenAI 兼容接口。
  • 降级路径：未配置密钥时，AI 出题入口明确提示"未配置模型"，同时提供本地模板出题；请求超时或网关错误时保留用户输入并提示重试，不产生半成品数据。
真实选型记录：接入阶段实测四个上游——某上游密钥欠费直接失败；某上游在 gpt-6.1-sol 上单次出题超过 60 秒触发网关 504；改用 gpt-6-astra 后 21 秒完成并成功入库。因此把"请求超时"作为一等公民处理，而不是假设模型总是及时返回。

2.4 第四层：可观测与可回退

  • 连接状态卡：设置 → AI 模型与 API 实时显示服务地址、模型名、密钥掩码、配置状态，并提供"刷新状态"。
  • 诊断导出：一键导出 JSON，包含版本、模型配置（脱敏）、工作区数据库清单、最近错误，便于复盘。
  • 可回退：流程实例使用发布时的流程快照，改版不影响在途申请；应用蓝图为增量变更，保留既有数据与字段 ID；工作区支持导出备份与恢复。

3. 总体架构设计

3.1 分层结构

表现层原生 ES 模块 SPA（hash 路由）+ 桌面壳增强样式（desktop-shell.css）+ 八引擎独立命名空间
↓ 同构复用同一套前端资源
桌面层Electron 主进程（窗口/托盘/数据目录）+ preload（最小权限桥）+ 内嵌本地服务（端口 3102）
↓ HTTP
服务层server.mjs 静态与路由（网页端 3100）+ src/*-service.mjs 八模块数据服务、认证、备份、ai-config
↓
数据层桌面：8 个 SQLite 数据库（node:sqlite，位于 %APPDATA%\OmniFormOS Desktop\workspace\）
网页：localStorage / sessionStorage 原型数据
↓
模型层/api/ai/config 统一配置 → OpenAI 兼容上游（base_url / model / api_key 运行时可切换）
图 1　OmniFormOS 五层架构

3.2 双运行形态与单一源码

网页端与桌面端使用同一套 public/ 与 src/ 源码，差异仅在三处注入：

  1. 端口：网页 3100，桌面内嵌服务 3102；
  2. 数据根：桌面把数据库路径指向用户目录，网页使用浏览器存储；
  3. 样式与能力：preload 注入 omni-desktop 根类，启用桌面壳布局、窗口控制与个人中心抽屉。

这样评审只需理解一套代码，也避免了原型与正式版功能漂移。仓库提供 npm run desktop:sync，以仓库为唯一真源把源码同步到本机安装副本。

3.3 模块边界

  • 命名空间隔离：每个引擎使用独立前缀（formpilot*、examcraft*、flowform*、docmorph*、adaptform*、tablemind*、labform*、appcanvas* / canvas-*），避免样式与函数名冲突。
  • 服务边界：每个引擎对应一个 src/*-service.mjs，路由挂载集中在 server.mjs，模块之间不直接引用彼此内部实现。
  • 数据边界：每个引擎独立 SQLite 文件，跨模块协作通过工作台事件与显式数据授权入口（如 ExamCraft 结果嵌入 FormPilot 应用）。
  • 共享能力：主题变量、双语引擎、账户与设置作为工作台层提供，不下沉到具体引擎。

4. AI 生成代码的架构约束与质量门禁

本项目大量代码由 AI 在明确约束下产出。约束的意义在于：让"生成"可控，让"评审"可验证。以下五条是实际执行中最有效的约束。

4.1 约束一：主题必须走变量分层

禁止在模块内写死颜色，统一使用主题变量（--desk-* 与 --module-*）。深色主题通过专用层级覆盖，不允许用全局 !important 粗暴重绘——这一条来自两个真实事故：

  • 事故 A：深色主题下窗口左上角红黄绿三色按钮全部变灰。根因是深色修复样式里存在一条针对所有 button 的 !important 背景规则，覆盖了专用色。修复方式不是加更强的 !important，而是把三颗按钮的专用选择器提升到明确的作用域，并将该全局规则限定在内容区。
  • 事故 B：深色侧边栏所有导航项都呈蓝紫色底，看起来全部处于「选中」状态。根因同样是全局按钮规则叠加。修复方式是建立中性石墨层级（背景 / 悬浮 / 选中三档）并让普通项透明化。

4.2 约束二：界面文案与业务数据分离

所有界面文案经统一翻译引擎处理（精确词条表 + 词组替换 + 动态节点监听），业务数据（用户输入、导入内容、持久化记录）不参与翻译。双语切换必须覆盖：文本节点、placeholder、title、aria-label。

这条约束的实践代价很高：初版漏掉了动态渲染节点与属性文本，导致二级页面出现「可视化编辑器复用现有 React Flow」这类中英拼接。最终用自动化巡检（无头浏览器遍历 150+ 子页面入口，扫描 CJK 字符）替代人工目测，才把残留清零。

4.3 约束三：渲染安全

  • 所有用户可控内容进入 DOM 前统一转义（esc()），列表与详情页无例外；
  • 动态 HTML 拼接仅允许来自内部模板函数，禁止直接插入模型输出；
  • 桌面 preload 仅暴露最小必要能力（窗口控制、打开数据目录、版本号），不暴露 Node API。

4.4 约束四：变更必须可验证

门禁内容命令
语法检查130+ 文件逐一 node --check，覆盖前端与服务端npm run check
单元测试41 个测试文件：模型校验、服务层、工作台交互、物理动效、审计回归npm test
实机验证桌面端刷新后截图核对布局、深浅主题、双语、交互入口人工/自动化截图
双部署一致性仓库源码与安装副本逐文件比对，或一条命令同步npm run desktop:sync
版本一致性设置页版本号运行时读取 package.json，禁止多处手写—

4.5 约束五：渐进式重构而非推倒重来

桌面主页的引擎入口经历"胶囊快捷入口 → 扇形卡片 → 双形态可切换"的演进。最终方案保留原形态并新增形态，用户偏好持久化，避免为视觉新鲜感牺牲已习惯的操作路径。这类决策的判断标准是：新增能力不降低既有效率。

5.5 数据与隐私边界

  • 桌面版数据仅存本机 %APPDATA%\OmniFormOS Desktop\，不上传服务器；
  • AI 请求仅发送用户主动提交的内容（需求描述、大纲文本、待解析文档文本），不发送本地数据库整体；
  • 账户密码以加盐 SHA-256 哈希保存在本地，个人资料导出功能明确排除密码哈希、盐与头像数据。

6. 八大引擎功能说明

6.1 FormPilot —— 需求到应用

输入业务需求或选择场景模板，生成多实体应用蓝图（实体、字段、关联、角色操作、页面结构）。支持指令式增量迭代（"添加字段：预算，类型：数字，必填"），新增实体自动配套列表/表单/详情页。预览运行时可增删改查，关联字段从目标实体选择，被引用记录禁止删除以保护引用完整性。

6.2 ExamCraft —— 测评全流程

支持 TXT 大纲与 JSON 题库导入；AI 出题（结构校验后入库）与本地模板出题双路径；题库编辑与即时预览；试卷拖拽排序与题型分值配置；发布后学生端答题；客观题自动评分、简答题关键词建议与人工确认；成绩分析与覆盖度看板。

6.3 FlowForm —— 审批流程

按描述生成流程草稿，在画布上编辑节点、分支与审批人；发布前做图结构校验（起止节点、连通性、审批人非空）；发布后可发起申请，按串行节点流转，支持驳回、撤回、时间轴、本地通知与审计导出。实例绑定发布快照，流程改版不破坏在途单据。

6.4 DocMorph —— 文档数字化

导入 PDF、DOCX、XLSX、扫描图片与 TXT；本地中英文 OCR；原件预览与左右对照，字段标注来源页码与坐标；字段类型、选项、限制可人工校正与复核；校正结果可直接送入表单设计器生成可填报表单。原件保存在本地 IndexedDB，不上传。

6.5 AdaptForm —— 智能表单

表单规则引擎支持条件显隐、必填联动与校验；提供渲染器把表单定义渲染为可填报页面；提交数据进入分析视图，可查看分布与完成度。

6.6 TableMind —— 数据分析

导入表格数据，自动识别字段类型；支持聚合计算（求和、均值、计数、分组）、图表与仪表盘组合；数据工作台提供筛选、排序与导出，服务于快速验证数据假设。

6.7 LabForm —— 科研实验

记录实验批次、条件参数与观测结果；支持绘图与拟合展示；结果数据可导出用于报告撰写，适合课程实验与小型课题组日常记录。

6.8 AppCanvas —— 可视化应用搭建

拖拽式画布，组件遵循统一协议（属性、数据绑定、事件）；构建结果可由应用运行时加载，形成可交互页面；画布作品保留用户自定义配色，不被深色主题强制覆盖。

7. 工程过程与 AI 协作方式

7.1 演进记录

7.3 两个典型 Bug 复盘

案例一：深色主题元素被全局规则染色

现象：窗口控制按钮失去红黄绿；侧边栏所有导航项呈蓝紫色；主页输入框内部出现与背景割裂的色块。
根因：深色主题修复样式引入了针对通用标签（button、input、textarea）的高优先级规则，作用域过宽，覆盖了组件专用样式。
修复：为组件建立专用作用域与更高的界面层级选择器；把通用规则限定在内容区；输入区建立独立的中性色层级（输入面 / 边框 / 占位文字 / 控件）并整体校色。
教训：主题修复应从变量分层入手，禁止用全局 !important 覆盖。

案例二：双语切换在二级页面失效

现象：一级页面正常，进入模块内部后出现中英拼接与未翻译文本。
根因：三重叠加——词典缺失深层词条、动态渲染节点绕过翻译、ES 模块磁盘缓存复用旧词典。
修复：补齐深层词典；放宽对动态业务节点的跳过规则并把整句优先于词组匹配；给翻译入口与模块导入加版本号强制刷新；编写无头浏览器巡检脚本逐层扫描。
教训：涉及运行时状态的问题，必须用自动化巡检而非人工目测验收。

8. 已知限制与后续规划

8.1 当前限制

  • 桌面版为单机应用，不含多用户实时协同与服务端权限隔离；角色配置为建模属性，不执行真实鉴权。
  • AI 能力依赖第三方兼容接口，可用性与延迟受上游影响；出题质量仍需人工复核。
  • DocMorph 对手写体与旧版 DOC/XLS 支持有限，OCR 结果必须人工核对。
  • FlowForm 审批为串行模型，未实现并行会签与外部通知渠道。

8.2 规划

  • 模型路由：按任务类型（出题/抽取/生成）自动选择模型并带超时重试。
  • 工作区多项目管理与模板市场：把已验证的应用蓝图导出为可复用模板。
  • 审计与回滚增强：蓝图版本历史与一键回滚。
